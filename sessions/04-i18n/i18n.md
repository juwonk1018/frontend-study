# 라이브러리 비교

```
i18next ──────▶ react-i18next ──────▶ next-i18next
(순수 JS 코어)    (React 바인딩)        (Next.js 통합)

use-intl ─────▶ next-intl
(React 코어)     (Next.js 통합: proxy, navigation, 서버/클라 경계)
```

|             | i18next 계열                                              | next-intl                                |
| ----------- | --------------------------------------------------------- | ---------------------------------------- |
| 출발점      | 순수 JS. 프레임워크 비의존                                | React. Next.js에 최적화                  |
| 메시지 문법 | `{{name}}`, `key_one` / `key_other`                       | ICU MessageFormat `{count, plural, ...}` |
| 리소스 공유 | 하나의 JSON을 **React · React Native · Node 서버**가 공유 | `use-intl`로 React/RN 공유 가능          |
| 생태계      | backend 플러그인, 언어 감지기 등 폭이 넓음                | Next.js 안에서 필요한 것을 내장          |

# i18next 계열: 하나의 JSON, 여러 런타임

```json
// locales/ko/common.json
{ "greeting": "{{name}}님, 안녕하세요", "item_other": "{{count}}개" }
```

```typescript
// Node 서버, React Native, Next 모두 같은 파일을 읽습니다
import i18next from 'i18next';
await i18next.init({ lng: 'ko', resources: { ko: { common } } });
i18next.t('greeting', { name: '주원' }); // "주원님, 안녕하세요"
```

- 코어가 프레임워크를 모르기 때문에, **번역 리소스가 조직의 공통 자산**이 될 수 있습니다.
- 반대로 Next.js에서 필요한 locale 감지, 서버/클라이언트 인스턴스 분리, `Link` 래핑 등은 **직접**해야 합니다.
- 의존 관계: `i18next → react-i18next → next-i18next`
  - 2026년 3월 **v16부터 next-i18next가 App Router를 지원**합니다.

# next-intl은 Next.js에서만 생기는 고민을 대신 처리합니다

```typescript
// src/i18n/routing.ts
export const routing = defineRouting({
  locales: ['ko', 'en'],
  defaultLocale: 'ko',
  localePrefix: 'as-needed', // 'always' | 'as-needed' | 'never'
});
```

```typescript
// src/proxy.ts  (Next 16 이전에는 middleware.ts)
export default createMiddleware(routing);
export const config = { matcher: '/((?!api|_next|_vercel|.*\\..*).*)' };
```

- **locale 감지**: URL → 쿠키 → `Accept-Language` → 기본값 순으로 감지하여 locale 결정
- **서버/클라이언트 경계**: `getTranslations`(서버) / `useTranslations`(클라이언트), 메시지는 요청 단위로 주입
- **Navigation API**: `createNavigation(routing)`이 locale이 붙은 `Link`, `redirect`, `usePathname`을 제공

---

| 직접 구현 시                                               | next-intl                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------- |
| `[lng]` 파라미터를 읽어 **요청마다** i18next 인스턴스 생성 | 요청 단위 설정 파일 하나 (`i18n/request.ts`)               |
| 서버용 초기화와 클라이언트용 초기화를 **따로** 작성        | `getTranslations` / `useTranslations` 또는 `getT` / `useT` |
| 쿠키·헤더로 언어 감지 후 리다이렉트하는 미들웨어           | `createMiddleware(routing)` / `createProxy(config)`        |
| `/about` → `/ko/about`로 바꿔주는 `Link` 래퍼              | `createNavigation(routing)`                                |
| 클라이언트에 서버 리소스를 다시 넘겨 hydration             | `NextIntlClientProvider` / `I18nProvider`                  |

> 두 라이브러리의 차이는 "번역을 할 수 있는가"가 아니라, **Next.js의 라우팅·렌더링 모델과 얼마나 맞물려 있는가**였습니다.

# 번역 파일의 공유: SSOT를 어디에 둘까

| 방식           | 구조                              | 장점                                    | 비용                                             |
| -------------- | --------------------------------- | --------------------------------------- | ------------------------------------------------ |
| **모노레포**   | `packages/locales/ko/common.json` | 변경이 한 커밋에 담김. 타입 공유 쉬움   | 모노레포 전제                                    |
| **npm 패키지** | `@org/locales` 배포               | 레포가 분리돼도 SSOT 유지               | 패키지 갱신 후 **의존 서비스 재배포** 필요       |
| **CDN (S3)**   | 런타임에 JSON fetch               | 재배포 없이 번역 수정, 런타임 언어 추가 | **캐시 정책** 설계, 배포 타이밍과 어긋날 수 있음 |

<br/>

- npm 패키지는 "코드와 함께 검증되어 배포된다"는 안정성을, CDN은 즉시 반영되는 효과를 얻습니다.
- CDN은 번역 키와 코드가 **따로 배포**되므로, 버전 관리(`/v12/ko/common.json`)로 묶거나 짧은 `max-age` + `stale-while-revalidate`가 필요합니다.

# Next.js에서의 번역 파일 위치: 빌드 타임 vs 런타임

|           | `app/i18n/locales/`                         | `public/locales/`                |
| --------- | ------------------------------------------- | -------------------------------- |
| 로딩      | `import()`로 **빌드 타임 번들**             | **런타임 HTTP 요청**             |
| 반영 시점 | 배포와 함께                                 | 파일 교체 즉시                   |
| 장점      | 빠름, 누락 시 빌드에서 발견, 타입 생성 용이 | 재배포 없이 수정, 언어 동적 추가 |
| 주의      | 번역 수정에도 재배포                        | 네트워크 1회 추가, 캐시 무효화   |

```typescript
// next-i18next v16: resourceLoader를 주면 번들, 생략하면 public/locales를 읽습니다
resourceLoader: (lng, ns) => import(`./app/i18n/locales/${lng}/${ns}.json`);
```

> 일반적으로는 **빌드 타임 번들**이 기본값. 운영팀이 번역을 수시로 바꾸는 서비스에서만 런타임 로딩 고려

# 서버 응답에 번역이 담겨 올 때

**UI 문자열**과 **콘텐츠 데이터**를 먼저 분리합니다.

| 종류        | 예                       | 소유     | 처리                       |
| ----------- | ------------------------ | -------- | -------------------------- |
| UI 문자열   | 버튼, 라벨, 빈 상태 문구 | FE       | 번역 파일                  |
| 콘텐츠      | 상품명, 공지, 게시글     | BE / CMS | API가 locale에 맞춰 응답   |
| 에러 메시지 | "재고가 없습니다"        | FE       | BE는 **코드**만, FE가 번역 |

- API에는 `Accept-Language` 헤더나 `?locale=ko`로 언어를 전달합니다. 캐시가 있다면 `Vary: Accept-Language` 또는 URL에 locale 포함이 필요합니다.
- 에러를 문장으로 내려주면 사용자가 언어를 바꿔도 **이전 언어의 메시지**가 남습니다. 코드 → FE 매핑이 안전합니다.
- Node 백엔드가 i18next JSON을 **공유**하면 서버에서 문장을 만들어야 할 때(이메일, 푸시)도 같은 리소스를 씁니다.

# Q. 언어 구분 방식 비교

| 방식                       | URL 예                   | SEO                    | 링크 공유 | 캐시       | 비용                                             |
| -------------------------- | ------------------------ | ---------------------- | --------- | ---------- | ------------------------------------------------ |
| **경로 prefix** (`always`) | `/ko/about`, `/en/about` | ◎ 언어별 URL, hreflang | ◎         | ◎ URL 기준 | 모든 라우트가 `[locale]` 아래                    |
| **서브도메인**             | `ko.example.com`         | ◎ 지역 신호 강함       | ◎         | ◎          | 인증서·DNS·로컬 개발, **쿠키가 도메인별로 분리** |
| **쿠키/헤더만** (`never`)  | `/about`                 | ✕ 크롤러는 한 언어만   | ✕         | ✕          | 가장 단순                                        |
| 쿼리                       | `/about?lang=ko`         | ✕ 중복 콘텐츠          | △         | △          | 비권장                                           |

> `/about/ko` 처럼 뒤에 붙이면 **모든 라우트마다** `[lng]/page.tsx`를 만들어야 합니다. 앞에 두면 `app/[locale]/` 하나로 끝납니다.

# Q. 복수형 표기

`Intl.PluralRules`는 CLDR 규칙으로 숫자를 `zero · one · two · few · many · other` 중 하나로 분류합니다.

```typescript
new Intl.PluralRules('en').select(1); // "one"
new Intl.PluralRules('en').select(2); // "other"
new Intl.PluralRules('ko').select(1); // "other"  ← 한국어는 항상 other
new Intl.PluralRules('ru').select(2); // "few"    ← 러시아어는 4가지
```

```json
// i18next: count를 넘기면 접미사로 분기. ko는 _other 하나만 있으면 됩니다
{ "item_one": "{{count}} item", "item_other": "{{count}} items" }
```

```json
// next-intl (ICU): 메시지 안에서 분기
{ "item": "{count, plural, one {# item} other {# items}}" }
```

> 복수형 체계는 **한국어를 위해서가 아니라 번역 대상 언어를 위해** 필요합니다. 영어·러시아어·아랍어를 추가할 때 코드를 고치지 않으려면 처음부터 `count`를 넘기는 습관이 중요합니다.

# Q. 조사: 변수 뒤에 붙는 은/는, 이/가, 을/를

문제: `"{{name}}이 도착했습니다"`

**접근 1. 문장을 고쳐 조사를 피한다**
`"{{name}}님이 도착했습니다"`, `"도착: {{name}}"` 처럼 조사가 **고정 명사** 뒤에 오게 구성합니다.

**접근 2. 코드에서 조사를 계산해 인자로 넘긴다**

```typescript
import { josa } from 'es-hangul';
t('arrived', { name: josa(name, '이/가') }); // 메시지: "{{name}} 도착했습니다"
```

# Q. 언어별 폰트 다르게 지정하기

**1단계. `lang` 속성을 반드시 넣는다**

```tsx
// app/[locale]/layout.tsx
<html lang={locale} className={`${inter.variable} ${pretendard.variable} ${notoJp.variable}`}>
```

**2단계. `:lang()` 선택자로 폰트를 바꾼다**

```css
:root {
  font-family: var(--font-inter), var(--font-pretendard), sans-serif;
}
:lang(ko) {
  font-family: var(--font-pretendard), sans-serif;
}
:lang(ja) {
  font-family: var(--font-noto-jp), sans-serif;
}
```
